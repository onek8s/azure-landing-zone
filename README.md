# azure-landing-zone

The Azure landing zone of [OneK8s](https://onek8s.github.io/) - one Kubernetes platform for every cloud, which runs
in any public cloud without changes to the applications or to how they are deployed. Azure is the first cloud
implemented; this repository is its landing zone, built with the
[Azure Landing Zones IaC Accelerator](https://azure.github.io/Azure-Landing-Zones/accelerator/) (Terraform, Azure
Verified Modules). The clusters and the container registry are
[aks-terraform](https://github.com/onek8s/aks-terraform)'s; what runs in them is
[aks-fluxcd-platform](https://github.com/onek8s/aks-fluxcd-platform)'s. Portability:
[design section 1.3](https://github.com/onek8s/onek8s.github.io/blob/main/design/1.3-open-standards-and-portability.md).

It implements **phase 1 (Foundation)** of the
[implementation project](https://github.com/onek8s/onek8s.github.io/blob/main/archive/7.1-implementation-project-and-acceptance-testing.md):
a separate build tenant with management, hub and `sub-aks-dev`, pipelines with OIDC, all Azure Policy assignments in
audit mode and a client VNet that simulates the corporate network, in **germanywestcentral** (since 2026-10-15; the
accelerator bootstrap stays in swedencentral). `sub-aks-dev` plays the design's internal dev subscription
`sub-aks-dev-int` (decision D52: internal and external workloads have a subscription and clusters each); the build
tenant has no external one now. The dev environment's cluster - one internal stateless cell
`aks-dev-int-stateless-az3` (Azure CNI Pod Subnet) with Sweden's zone `int-se`, its network and Key Vaults - is
[aks-terraform](https://github.com/onek8s/aks-terraform)'s, created and deleted by its pipeline in `sub-aks-dev` with
this repository's dev apply identity, and routed through labfw in the hub (network mode `labfw`).

**Start here: [docs/deployment.md](docs/deployment.md)** · Lab without Azure Firewall: `scripts/set-network-mode.sh sandbox`, or with [labfw](https://github.com/onek8s/azure-lab-fw) instead of it (and a VPN for machines outside Azure): `scripts/set-network-mode.sh labfw` · Lab SKUs: [docs/deployment.md](docs/deployment.md#lab-skus) · Requirements → code: [docs/design-mapping.md](docs/design-mapping.md)

## Traffic flow documentation

[`docs/traffic-flows/`](docs/traffic-flows/README.md) shows, per application namespace and per isolation zone, what reaches the
application and what it reaches through the hub firewall - with the application that asked for each rule, which the
firewall itself cannot tell (OneK8s design section 5.3). The pages are generated from the rule files in
`stacks/platform-extensions/firewall-applications/` and the applications' own configuration; do not edit them by hand.

## labfw's log and its summaries

labfw writes its denied connections (AZFW column names) to the Log Analytics workspace `log-labfw-germanywestcentral`,
table `LabfwFirewallLog_CL`, where the egress agent reads them. Three summary rules there
([`modules/firewall-log-summaries`](modules/firewall-log-summaries/README.md), design D84) aggregate it into
`FirewallDeniedFlows_CL` and `FirewallRuleHits_CL` every hour (90 days) and `FirewallZoneTraffic_CL` every day
(395 days), each source attributed to its environment and isolation zone (or `system`, `shared`, the build tenant's
`management`, `client`, `vpn`, `hub`, else `other`); a bin shows up 1-2 hours after it closes, the daily one the next
day. The workspace takes no public queries: check from the labfw VPN or the portal - the workspace's *Summary rules*
blade lists the three rules, and

```kusto
FirewallDeniedFlows_CL | where TimeGenerated > ago(3h) | summarize sum(Count) by Zone, Destination
FirewallRuleHits_CL | summarize sum(Count) by Zone, Action, Rule, ActionReason
LASummaryLogs | summarize count() by RuleName, Status
```
